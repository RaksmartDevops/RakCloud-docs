本页导航

本节介绍调用 API 时如何处理错误，以及哪些情况适合自动重试。

是否可以重试 ​

情况是否重试说明
429可以等待后重试，采用指数退避
502视请求类型而定服务暂时不可用，见下文
网络超时、连接中断视请求类型而定见下文
400不应重试修正请求参数后再发起
401不应重试检查 API Key
404不应重试检查资源 ID 与账户
409不应立即重试先查询资源状态，满足条件后再操作

查询类请求 ​

GET 请求不会改变资源状态，遇到 429、502 或网络错误时可以直接重试。

操作类请求 ​

POST 操作类请求会改变资源状态。如果请求发出后出现超时、连接中断或返回 502，您无法确定指令是否已经下发，此时请不要直接重试：

  1. 调用详情接口，查询资源当前状态。
  2. 如果状态已经变化或正在变化，说明指令已经下发，无需重试。
  3. 如果状态未发生变化，再重新发起操作。

设置超时时间 ​

建议为每个请求设置客户端超时时间，例如 30 秒，避免程序长时间等待。

推荐的重试策略 ​

  • 采用指数退避：第 1 次等待 1 秒，第 2 次等待 2 秒，第 3 次等待 4 秒，依此类推。
  • 设置最大等待时间，例如 30 秒，以及最大重试次数，例如 5 次。
  • 超过最大重试次数后停止重试，记录错误信息和 X-Request-Id。

记录请求信息 ​

为便于排查问题，建议在日志中记录以下信息：

  • 请求方法与路径
  • HTTP 状态码
  • 响应头中的 X-Request-Id
  • 响应体中的 error_message

注意

请勿在日志中记录 API Key。
